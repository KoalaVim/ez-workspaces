## Context

The shell wrapper function (generated by `ez init-shell`) wraps the `ez` binary in a `while true` loop. When the binary writes to `post_cmd_file`, the wrapper sources those commands and re-invokes `ez` with `--repo <cd-target>`. This loop was designed for the browser flow: after a plugin bind action (e.g. killing a tmux session), the browser re-opens so the user can pick another session.

The problem: `accept_session` writes session env exports (PR metadata like `ez_pr_number`) to `post_cmd_file` for ANY session with env vars. The shell wrapper treats this as a re-launch signal, re-invoking `ez session enter <name> --repo <worktree-path>`. The second invocation fails because `resolve_repo(Some("<worktree-path>"))` calls `find_by_name_or_id`, which only matches repo names/IDs, not worktree paths.

## Goals / Non-Goals

**Goals:**
- `ez session enter` works for sessions with env vars (PR metadata, custom env)
- The browser's re-invoke-after-plugin-bind behavior is preserved
- All shell variants (bash/zsh, fish, pwsh) are fixed

**Non-Goals:**
- Making `resolve_repo` handle arbitrary worktree paths (separate concern)
- Changing how session env vars are propagated to the parent shell

## Decisions

### Use a `#EZ_RELAUNCH` comment marker in post_cmd_file

**Decision**: The Rust code writes `#EZ_RELAUNCH` as a line in `post_cmd_file` only when re-invocation is intended. The shell wrapper checks for this marker before looping.

**How it works**:
- `write_post_commands` continues to write normally (no marker)
- A new `write_relaunch_marker` function appends `#EZ_RELAUNCH\n` to `post_cmd_file`
- Called only in `session_action_loop` when a plugin bind action has effect (returns `cd_target` or `post_shell_commands`) and the browser exits
- The shell wrapper always sources `post_cmd_file` (env exports, tmux commands, etc.), but only loops when the marker is present

**Why not fix `resolve_repo` instead?** That would mask the real problem — the re-invocation itself is unnecessary for one-shot commands. It adds latency (extra binary execution) and complexity (new resolution paths).

**Why not skip writing env exports to post_cmd_file?** Session env vars (PR metadata) need to reach the parent shell. The shell wrapper's `source` is the mechanism for this; removing it would break env propagation.

**Why not use a separate file for the relaunch signal?** Adding a fourth temp file complicates the shell wrapper and the Rust code. A comment marker in the existing file is simpler — `#` is a no-op when sourced by all target shells.

## Risks / Trade-offs

- [Binary/wrapper version mismatch] → Old wrapper + new binary: relaunch marker is a harmless comment, but old wrapper still loops unconditionally (same bug as today). New wrapper + old binary: wrapper never finds marker, never loops (breaks browser re-launch after plugin bind actions). Mitigation: this is the same pattern as existing wrapper updates; users re-run `eval "$(ez init-shell zsh)"` after updating.
- [grep overhead in wrapper] → The wrapper runs `grep -q` on a tiny file per ez invocation. Negligible (~1ms). Alternative: check via env var set by sourcing, but comment marker is simpler.
